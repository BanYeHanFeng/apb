# 构建与测试

本文汇总 `apb` 的本地构建、静态 musl 交叉编译、构建工作流、测试与发布方式。
运行方式、命令契约和 GitHub Actions 临时节点见 [使用手册.md](使用手册.md)。

---

## 准备二进制

本机可跑 Rust 工具链时，直接原生构建即可：

```bash
cargo build --release --locked
# 产物：target/release/apb
```

在临时 VPS / CI / 构建容器里可交叉编译静态 musl 单文件（推荐用于 Termux 和 runner）：

```bash
rustup default stable
rustup target add x86_64-unknown-linux-musl aarch64-unknown-linux-musl
cargo install cargo-zigbuild --locked
python3 -m pip install --user ziglang

# x86_64 Linux / GitHub Actions runner
cargo zigbuild --release --locked --target x86_64-unknown-linux-musl

# aarch64 Android / Termux
cargo zigbuild --release --locked --target aarch64-unknown-linux-musl
```

产物：

- `target/x86_64-unknown-linux-musl/release/apb`
- `target/aarch64-unknown-linux-musl/release/apb`

## 构建与发布

`.github/workflows/ci.yml`（名称：`构建与发布`）把构建校验与发布合并为一个工作流：

- push `main` / PR / 手动触发（不填 tag）：运行 `测试（本机）` 和 `静态构建 <target>`；
- push `main` 且提交标题严格为 `发布: vxxx`（例如 `发布: v0.1.1`）：自动创建 tag（`v0.1.1`），构建并发布为 latest 正式版；
- push `main` 且提交标题不是发布格式：构建并更新唯一的预发布 Release；预发布固定使用 tag `pre-release`，并设置 `prerelease: true` / `make_latest: false`，后续普通推送复用同一个 Release 并覆盖其中的静态二进制；
- push `v*` tag：由 tag 触发，测试和构建通过后发布为 latest 正式版；
- 手动触发 `workflow_dispatch` 并填写 tag：发布对应标签；不填 tag 则只构建。

`静态构建 <target>` 任务用 Zig 交叉编译 `x86_64-unknown-linux-musl` 和 `aarch64-unknown-linux-musl`，
上传静态单文件；发布任务直接复用这些产物，不再重复构建。GitHub 会记录构建产物与 Release 资产的
SHA-256 摘要，无需另外生成 / 上传 `.sha256` 文件。

CI 通过缓存复用依赖与可复用的编译结果：`测试（本机）`、`静态构建 <target>` 和 `apb 临时节点` 都使用
`Swatinem/rust-cache`；两个 musl target 使用独立缓存键，避免不同架构的产物互相覆盖。Zig 由
`mlugg/setup-zig` 安装并缓存，`cargo-zigbuild` 由 `taiki-e/install-action` 下载预编译二进制并校验
checksum，不再每次 `cargo install --locked` 从源码编译。PR 连续推送会自动取消旧的未完成运行；
各 job 也设置了超时，避免异常时长时间占用 runner。

工作流里的第三方 action 使用 Node 24 运行时的大版本（`actions/*` v7 / v8、`softprops/action-gh-release`
v3）；GitHub 自 2026-06-16 起默认用 Node 24 执行 action，仍停留在 Node 20 的 action 会被强制升级并产生
弃用告警。`mlugg/setup-zig` 目前仍声明 `node20`，属于上游未跟进，暂由 runner 强制运行在 Node 24。

Rust 依赖的大版本以 `Cargo.toml` 为准（当前 `snow` 0.10、`sha2` 0.11、`getrandom` 0.4、`libc` 0.2），
CI 用 `--locked` 构建，升级依赖后必须一并提交 `Cargo.lock`。`snow` 关闭了默认特性，只启用协议实际用到的
算法后端（`Noise_NNpsk0_25519_ChaChaPoly_BLAKE2s`）；不要打开它的 `std` 特性，否则会连带启用并未使用的
`ring` 后端，静态 musl 构建会多出一份需要 cc 交叉编译的 C / 汇编代码。

根目录的 `runApb.sh` 默认按 `apb-<target>` 命名下载 latest 正式版 Release 资产，因此首次使用默认通道前
需要至少成功发布一次包含 x86_64 / aarch64 产物的正式版。加 `--pre`（或 `APB_CHANNEL=prerelease`）可从
tag `pre-release` 的唯一预发布 Release 下载，适合正式版尚未发布、但想先使用 `main` 最新构建的场景。

## 开发与测试

```bash
cargo fmt --check
cargo test --locked --all-targets
```

`tests/e2e.rs` 会在 loopback 上拉起 `apb serve`、`apb agent`，验证 `exec`、`push`、`pull` 全链路，
不依赖 sshd、外部网络或配置文件；`测试（本机）` 同时用 `bash -n runApb.sh` 检查一键脚本语法。

## 目录

| 路径 | 内容 |
|---|---|
| `Cargo.toml` / `src/` | Rust 实现（单包多角色：server / agent / controller） |
| `tests/e2e.rs` | loopback 端到端测试 |
| `runApb.sh` | 客户端一键脚本：数字菜单管理 agent（启动/停止/重启/更新/状态/配置），按通道下载对应 Release 静态二进制，交互询问参数 |
| `.github/workflows/ci.yml` | `构建与发布` 工作流：单元测试 + Zig 静态交叉编译，正式版更新 latest、非正式版更新唯一预发布 |
| `.github/workflows/apb-agent.yml` | 用 Actions secrets 把临时 runner 接入服务端 |
| `docs/使用手册.md` | 架构、启动方式和命令契约 |
| `docs/构建与测试.md` | 本文：构建、测试与发布 |
| `docs/协议.md` | APB0 线协议说明（apb 0.1.0） |
| `docs/安全.md` | 威胁模型与加固说明 |
| `docs/故障排查.md` | 常见故障与排障 |
| `skills/apb/SKILL.md` | AI 可执行的速用手册 |
